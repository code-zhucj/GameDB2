# 单线程模型 vs 多线程模型

游戏服务器数据引擎的两种线程模型对比分析。

## 单线程模型

### 优点

- **无锁设计**：单线程天然串行，无需锁保护，数据结构可用非并发版本（HashMap 替代 CHM），零同步开销。
- **开发简单**：心智模型直观，状态变化完全可预测，不需要考虑并发可见性、重排序等问题。
- **调试容易**：执行完全确定性，相同输入必定相同输出，bug 可稳定复现。
- **快照回滚自然**：异常时用对象快照回滚，实现简单，无需考虑并发下快照一致性。
- **热更新友好**：无并发状态，代码热替换不需要处理正在并发执行的旧逻辑。

### 缺点

- **单核瓶颈**：压测 2000 人就到极限，无法利用多核 CPU。
- **长事务阻塞全局**：一个死循环或耗时操作阻塞全部后续任务，影响面覆盖全服所有玩家。
- **IO 必须异步**：事务内不能同步等待 IO（查 DB、RPC），必须异步回调。异步出去再回到主线程的代码有强烈割裂感，难以维护。
- **事务回滚受限**：异步 IO 模式下，回调链路中的状态变更无法纳入统一的事务回滚，只能靠补偿逻辑兜底。
- **快照开销不可省**：即使无并发，仍然需要对象快照来支持异常回滚。
- **跨服事务实现困难**：两个线程（服）之间的数据同步需要自己处理，不加锁的情况下很难设计安全协议。
- **全缓存依赖**：非全缓存方案下，DB 穿透 + 异步回调的组合让代码复杂度爆炸，通常被迫走全缓存路线，内存压力大。

## 多线程模型

### 优点

- **单进程承载更多玩家**：多核并行，突破单核 2000 人瓶颈，理论线性扩展到 N 核。
- **业务代码无需管理锁**：框架层的 LockKey + 排序加锁机制保证无死锁，开发者只需写业务逻辑。
- **玩家线程绑定后性能直逼单线程**：同玩家事务绑定同一线程，不需要锁、不需要 CHM、不计框架开销，达到单线程级性能。
- **跨玩家事务天然支持**：LockKey 按 (tableName, primaryKey) 排序加锁，跨玩家交易/组队等操作框架层统一处理，开发者无感。
- **影响面可控**：一个玩家的慢事务只阻塞同线程的其他玩家，不会拖垮全服。
- **IO 兼容性好**：事务内同步等待 IO 不会阻塞其他线程的玩家，代码结构保持同步风格，开发体验顺畅。
- **持久化方案灵活**：全缓存和非全缓存都能支持，IO 穿透不会破坏事务结构。
- **故障隔离**：一个线程 panic 不会杀掉所有玩家的数据。
- **架构可扩展性**：可利用现代多核 CPU，随着硬件演进持续受益。

### 缺点

- **框架固定开销**：锁获取、CHM 操作、队列调度等开销按事务份数累积，微小事务的场景下有可测量的性能损失。
- **框架设计复杂度高**：LockKey、事务日志、重试机制、死锁规避等都需要精心设计，维护门槛高。
- **GC 压力更大**：单事务对象分配更多（LogicFuture、Log 实例、Record.copy），在高并发下 GC 抖动更明显。
- **调试不具确定性**：时序依赖的 bug 难以稳定复现，需要更完善的日志和监控体系。
- **重试成本**：锁冲突时触发事务重试，虽然保证了正确性但增加了 CPU 开销。
- **同线程仍可能阻塞**：玩家线程绑定后，恶意事务仍可阻塞同线程玩家，虽然影响面大幅缩小。

## 设计初衷：为什么需要这个框架

### 两种现有方案的"不可恢复"缺陷

在实际项目中先后使用过单线程和多线程框架，各自遇到了**无法通过开发规范消除**的结构性问题。

#### 单线程方案的真实现状

- **无对象快照，数据不是强一致的**：异常发生时，同一行数据可能出现部分字段已修改、部分字段未写入的情况。比如一个事务改 3 个字段，改完第 1 个字段后抛异常，后 2 个字段保持旧值，数据进入非法中间态且无法回滚。
- **异步序列化导致数据撕裂**：为避免阻塞主线程，序列化落盘必须异步执行。异步线程读到的数据可能处在事务执行中途——A 字段是事务前的值，B 字段是事务后的值。落盘数据不是任何一个确定时间点的完整快照。
- **"最终一致性"只在正常关服时成立**：只有进程正常退出、最后一次全量刷盘才能保证数据完整。服务运行中任意时刻宕机，DB 中的数据很可能是错的，恢复后数据不可信。
- **可恢复性依赖运维运气**：宕机后数据错到什么程度、能不能修复，完全取决于宕机的时机，没有一个可靠的恢复基线。

#### 多线程方案的真实现状

- **死锁是概率问题，无法根除**：涉及多表操作时需要开发者手动确保加锁顺序一致。即使制定了规范、做了 code review、加了死锁打断和监控，线上仍然出现过测不到的死锁路径——因为不同功能模块的组合路径是 Code Review 无法穷举的。
- **死锁后果严重**：一个死锁环可以挂掉整个服务进程，影响所有在线玩家。线上为了防范加了一堆兜底机制（打断、超时、监控告警），但这些机制本身也增加复杂度，且都无法给出"绝对不会死锁"的承诺。
- **锁管理的认知负担全在开发者身上**：每次写跨表业务，开发者脑子里要同时想"我现在要锁哪些表？之前锁过什么？有没有别人也在锁这些？顺序对吗？"，这是出错率最高的环节。

### 本框架的解决思路

**核心目标**：在保证同步风格开发体验的前提下，用框架机制消灭上述两类问题，而不是靠开发者的纪律性。

#### 1. 永远不会死锁

LockKey 按 `(tableName, primaryKey)` **强制排序**后再加锁。这个排序不是"建议你这样做"，而是框架内部的固定流程——开发者调用 `table.select(id)` 或 `table.insert(entity)` 时，框架自动创建 LockKey 并按 TreeMap 排序，**开发者的代码里根本没有让你写锁的地方，所以也没有写出死锁的可能。** 从根源上消除了一整类线上事故。

#### 2. 数据始终保持权威

- **事务日志 + 对象快照**：事务修改写入日志而非直接改数据。commit 成功则一次性 apply 所有变更；异常则丢弃日志，数据原封不动。不存在"改了一半"的中间态。
- **writeLock 下制作落盘快照**：commit 时在持锁状态下复制一份数据的完整快照，释放锁后再交给异步持久化线程。快照对应的是某个确定的事务边界，**宕机后 DB 中的每行数据都处于事务完备状态**，不会出现数据撕裂。
- **可配置的持久化策略**：从"允许丢 N 秒事务"到 WAL 零丢失，取决于性能预算。**无论选择哪一档，数据的正确性都有保证——区别只在于丢多少事务，而不是数据会不会错。**

#### 3. 开发体验回归同步风格

- 事务内可以同步等待 IO，不影响其他线程的玩家。不需要把业务逻辑拆成 callback/promise 链。
- 开发者只需写 `Logic.process()`，框架处理事务隔离、锁管理、冲突重试、回滚——这些是**框架的职责**，不是业务代码的职责。
- 一个玩家的事务不会阻塞全服，影响面从"所有人"收窄到"同线程玩家"。

#### 4. 单线程级性能路径

应用层按玩家 ID 做线程绑定后，同玩家的事务在同一线程串行执行——不需要锁、不需要 CHM、零框架开销，性能和单线程模型持平。框架的 LockKey 机制**只服务低频的跨玩家操作**（交易、组队等），走的是"快路径 + 慢路径"分层策略。

### 一句话总结

> **单线程的正确性需要运气，多线程的正确性需要纪律，本框架将正确性变成了机制。**

| | 单线程 | 传统多线程 | 本框架 |
|---|---|---|---|
| 数据正确性保证 | 依赖正常关服 | 锁顺序不出错 | ✅ 框架强制 |
| 死锁风险 | 无需锁 | 概率存在 | ✅ 数学上不可能 |
| 开发者锁管理 | 无 | 必须手动 | ✅ 无需关心 |
| 宕机可恢复性 | 不可靠 | 取决于实现 | ✅ 事务完备 |
| 多核利用 | ❌ | ✅ | ✅ |
| 性能路径 | 单核最优 | 取决于锁实现 | ✅ 快慢分层 |

## 综合对比

| 维度 | 单线程 | 多线程 |
|---|---|---|
| 单服承载上限 | ~2000 人 | N 核 × 数千人 |
| 事务内 IO | 困难（callback hell） | 自然（同步风格） |
| 跨玩家数据操作 | 需要自建协议 | 框架原生支持 |
| 慢事务影响面 | 全服 | 同线程玩家 |
| 开发心智负担 | 低（无并发） | 低（框架屏蔽锁） |
| 框架维护负担 | 低 | 中高 |
| 内存方案灵活度 | 倾向全缓存 | 全缓存/按需加载均可 |
| 多核利用率 | 单核 | 接近线性 |
| 调试难度 | 低 | 中 |
| 热更新 | 简单 | 需额外处理 |

## 适用的游戏类型

| 游戏特征 | 推荐模型 |
|---|---|
| 休闲/棋牌/IO 类，同屏交互极少 | 单线程足矣 |
| MMORPG/卡牌/策略，玩家间有大量交易/战斗/公会 | 多线程 |
| 开房间对战的（MOBA/FPS），房间内高频交互、房间间隔离 | 按房间做线程绑定 + 多线程 |
| 强社交 + 大世界 | 多线程 + 分区策略 |

## 建议的多线程架构策略

```
┌─────────────────────────────────────────┐
│                应用层                      │
│   playerExecutor[id % N] → 绑定线程       │
│   同玩家事务：直接在当前线程同步执行         │
│   跨玩家事务：走框架 LockKey + Submit       │
├─────────────────────────────────────────┤
│                框架层                      │
│   LockKey 排序加锁 → 无死锁                │
│   ThreadLocal 事务隔离                     │
│   子事务合并 / 回滚丢弃                     │
│   版本号 CAS → 冲突重试                    │
│   异步持久化（commit 时快照 → 异步落盘）    │
└─────────────────────────────────────────┘
```

核心原则：**高频路径（同玩家操作）走无锁直通，低频路径（跨玩家操作）走框架保护**，两者取其长。
